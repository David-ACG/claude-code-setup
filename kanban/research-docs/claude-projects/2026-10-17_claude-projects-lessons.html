What Claude Code Projects can teach the GWTH workflow

17 October 2026 · checked against the official docs that day · based on Chase AI's video (16 Oct) and the Projects docs

Projects puts one coordinator in front of many full Claude sessions running in Anthropic's cloud. It is the wrong place for GWTH work, but some of its ideas are well worth bringing into the setup you already have on hlab.

The short version

Recommendation: don't adopt Projects. Take six of its patterns into your own setup, starting with hard spending guards, then slimmer instructions, shared project memory, one set of states, warm-resume workers and finally a coordinator session.

  • Your usage worry is justified, and Anthropic says so. Projects "uses them faster". Threads that hit your limit carry on by themselves when it resets, so they spend your next window without asking.
  • It doesn't fit GWTH's local work. Cloud threads have no GPU and can't reach hlab, /data, TTS, Coolify or Tailscale. Your ~/.claude rules and skills aren't loaded. Local threads exist, but they are immature.
  • You already have about 70% of the plumbing: beads, hub Run, the cockpit, Firstmate, ship.py, flash-worker. What Projects adds on top is one front door, one set of states, one shared memory, and workers you can follow up with.
  • What you do better, and should keep: limits enforced in code, local hardware, cheaper models alongside Opus, and "live and proven" rather than "merged" as the meaning of done.

What Projects actually is

It is not the old claude.ai Projects, which were folders of chats. It launched on 17 Sep 2026 as a public beta for Pro and Max (not yet on Team or Enterprise), and works in the desktop Code tab, claude.ai/code and the mobile apps, but not in the terminal CLI.

The usage question, answered

Your worry is right. Here is everything in a project that uses your plan, and why each one matters to you.

What uses your planWhy it matters to you
Every running thread is a full session on Opus, high effort by defaultFive to fifteen parallel Opus-high sessions is the fastest burn there is. Your rule 09 (always the latest Opus at high effort) would make it worse here.
A thread that hits the limit retries and continues when the limit resetsYour next 5-hour or weekly window gets spent on old work without a word. Only Stop or Pause prevents it.
Idle threads wake up on CI failures and review commentsSpending you didn't start. You have to tell each thread to stop watching its PR.
Picking up a thread that has been idle for over an hour re-reads its whole conversationCold follow-ups are expensive. The docs advise starting a fresh thread instead.
Concurrency: no cap except 200 new threads a dayYour "max two" is a preference, not a limit.
The coordinator's own tokensSmall at low effort, but it runs for as long as work keeps arriving.

The safety net: a project can't go past your plan limits unless you have turned on usage credits, and "a thread can't turn them on for you". An idle or archived project uses nothing.

Measured numbers: I found no credible third-party measurement (weekly % per thread, tokens per project). The press repeats Anthropic's "reach limits faster" line. For scale, the docs' general cost page puts agent teams at about 7× the tokens of a single session in plan mode.

Projects moves control from code you own to preferences Claude keeps. Your setup does the opposite: locks, queues, single writers and timeouts. That is your advantage, and the recommendations below make it stronger.

Recommendations

In the order I would build them. Each card lists what to build, where it goes, and what it does to usage.

R1 Hard spending guards, before anything else

This is where Projects is weakest and you are strongest. Make it explicit.
  • Build on /usage, don't replace it. It already shows live 5h and 7d %, burn-up and pace alerts; the Claude lane has been live since 12 Sep. What's missing is anything that acts on those numbers, and a view by run.
  • Per-run budget. Every headless claude -p (night, track, hub, Firstmate) gets --max-turns on top of its timeout. Record the tokens from stream-json in hub_runs.yaml against the bead. Show it as a "by run" table on /usage: Projects' Usage tab, but per bead.
  • Start gate. No new worker starts while the weekly meter is above a threshold you choose (say 80%). It lives in code, as one helper called by every runner.
  • Pause-all. One cockpit button and one CLI flag stop every queue from starting new work.
  • Resume-at-reset, opt-in per job (resume_at_reset: true plus a spend ceiling). The default stays as it is now: hitting the limit counts as a failure.
~1 dayGWTH-launch-plan scripts/Saves usage

R2 One set of states, and one "Waiting on you" view

  • Adopt Projects' wording as the shared vocabulary: Proposed · Working · Waiting on you · Ready for review (on hlab, probed) · Landing (approved, publishing) · Idle · Resolved (live and proven, or parked after 7 days).
  • Map the existing states onto it. Ship ledger awaiting_review → Ready for review, approved → Landing, done → Resolved. Firstmate escalated, cockpit needs_input and board blocked → Waiting on you.
  • One read model (scripts/lanes.py), not a new store. The cockpit lanes view renders it, and the end-of-session link can always go straight to the item.
  • Night-run blockers become questions in Waiting on you, not failures plus a Telegram message. Use Firstmate's escalate-and-resume pattern.
1–2 daysGWTH-launch-plan + cockpitUsage neutral

R3 Project memory that headless workers read and write

  • New folder: GWTH-launch-plan/memory/ with a MEMORY.md index and one file per requirement, decision or pitfall.
  • Every worker prompt starts with "read memory/MEMORY.md". The index is cheap; files are opened only when needed.
  • Workers propose, one writer commits. The completion packet gains a Memory proposals section, hub_review.py accepts or rejects them, and project_memory.py is the only writer.
  • Keep Projects' split: repo facts go in that repo's CLAUDE.md. Facts that span repos go in project memory. Taste goes in the bible. Reference material goes in the wiki.
~1 dayGWTH-launch-planSaves over time

R4 A coordinator session as the front door for big projects

  • A long-running local "GWTH Coordinator" session on hlab, started from a coordinator skill. It runs on hlab, so it can reach everything local.
  • Its job is routing only:
    • answer quick questions;
    • turn new work into beads;
    • propose workers and wait for your go;
    • dispatch through hub_run.py;
    • read completion packets, never worker transcripts;
    • keep project memory up to date;
    • give you the one-line hand-over.
  • It never builds anything itself. That is what keeps Projects' coordinator cheap.
  • It survives compaction because it works from recent messages, the lanes view and project memory, the way Projects' coordinator does.
  • You reach it from your phone through the cockpit channel and /m/. The same skill works for other big projects with beads and a board.
2–3 daysskill + cockpit wiringSmall, steady usage (measure with R1)

R5 Workers you can follow up with: resume them warm, restart them cold

  • Store session_id per bead for every headless run. Firstmate already does this.
  • The rule, taken from the Projects docs' cache advice:
    • A follow-up within an hour resumes the session: claude -p --resume <sid>. The cache is still warm and the context carries over.
    • After an hour, start fresh with a hand-over note built from the completion packet and memory. Resuming a cold session re-reads the whole conversation at full price.
  • Optional standing workers for each area (website, pipeline-audio, films). Each keeps its last session, which matches Projects' "reuse a thread in the same area".
  • Talk to a worker from the cockpit, so you no longer need hand-written *-resume.md prompts.
~1 dayhub_run + run scriptsSaves on follow-ups

R6 Slim what every worker loads

  • Today: about 86,000 characters before a GWTH-launch-plan worker starts. Projects caps project instructions at 16,000, and the video's advice is "less is more".
  • Target: under 20,000 characters.
    • Move the long procedures in the 883-line CLAUDE.md (ship ledger detail, night scheduler, cockpit channel) into skills that load on demand. You did the same in June for kanban-gates and infrastructure.
    • Keep goals, routing and the non-negotiables in CLAUDE.md.
  • A lint check that fails when the always-loaded instructions go over budget.
~½ day + your reviewGWTH-launch-plan CLAUDE.mdSaves on every run

What not to copy

  • No  Idle workers waking up on CI failures or review comments. That is spending you didn't ask for.
  • No  Concurrency caps that are only requests. Keep yours in code: fleet.py max 3, the hub FIFO, the repo lock.
  • No  Opus at high effort for every task. The docs call it the fastest burn, and flash-worker and Codex are cheaper lanes Projects can't use.
  • No  Continuing automatically when a limit resets, unless the job has opted in (R1).
  • No  "PR merged = done". Done stays as probed on hlab, approved, then probed on Hetzner.

Optional: a capped one-week pilot of the real thing

Only if you want first-hand numbers. Pick one repo that is safe in the cloud: a GWTH_V2 UI task with no secrets and nothing on hlab. Set it up like this:

  • threads on Sonnet at medium effort;
  • the coordinator on low effort;
  • project instructions: "Propose threads and wait for my go-ahead. At most two at a time. Stop watching PRs when idle.";
  • usage credits off.

Record the weekly % before and after. I don't recommend this now. The patterns above get most of the value without the risk.

Suggested order and size

  1. R1 Spending guards
    A start gate that reads the /usage numbers, tokens per run on /usage, and Pause-all
    ~1 day · saves
  2. R6 Slim instructions
    Get always-loaded instructions down to ≤ 20k characters
    ~½ day · saves every run
  3. R3 Project memory
    Workers read and propose; one writer commits
    ~1 day · saves over time
  4. R2 One set of states
    The "Waiting on you" view; blockers become questions
    1–2 days · neutral
  5. R5 Warm resume / cold restart
    Store session_id per bead; apply the one-hour rule
    ~1 day · saves
  6. R4 Coordinator session
    Builds on R2 and R3; measured with R1
    2–3 days · small, steady

R1 comes first because every other change is easier to judge once you can see what each run costs. R4 comes last because it depends on R2 and R3.

What the video adds

Chase AI, "Claude Code's Secret Upgrade Is an Orchestration Beast" (16 Oct 2026, 18:49). In a 25-minute demo, the build split into five parallel threads. Two came back ready for review and three were blocked on API keys or decisions. The X-scanner thread ran locally because it needed his logged-in browser.

  • 8:20 Coordinator on low effort. "It's just the one coordinating." This matches the docs' default.
  • 8:55 Set threads to medium, or Sonnet, because of "5 10 15 sessions … at the same time 24/7". The default is high.
  • 9:40 Project instructions: "less is more".
  • 11:50 Debug access between projects. One project can look at another whose context has gone bad. This isn't in the docs page as I checked it.
  • 4:50 Boris Cherny uses Projects as a backlog "dumping ground". I couldn't verify this.

Corrections to the video:

  • Projects launched on 17 Sep, not "a couple months ago".
  • The waitlist and gradual rollout still apply.
  • "Never shut off" is overstated. Sandboxes pause between turns, and idle threads resolve after a week.
  • Threads share instructions and memory, not context windows.
